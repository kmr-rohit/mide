What a fast editor means here

A screen refreshes every 16 ms at 60 Hz. Typing feels instant when a keystroke costs much less than that, and nothing you trigger may block the interface. So each measurement has a budget set from what you would feel, and the results below show how much of it is used. A budget is a goal we hold ourselves to, not a number reverse-engineered from today's results.

What got faster by measuring

Benchmarks are only worth having if they find things. These were found, and fixed, along the way:

ProblemBeforeAfterFix
Jump to line 100,000 in a big file3.8 s12 msHighlight from a short warm-up above a far window instead of parsing every line before it.
Start to first editor paint334 msabout 165 msCheck for one font instead of listing every installed font, twice.
Idle CPU with a terminal openabout 8%under 1%Wake on terminal output instead of polling every 12 ms.
Closing a session whose program ignores hang-upfroze the appinstantWait for the process on another thread, with a forced stop after 1.5 s.
Find a match near the end of a 1,000,000-line file269 msunder 1 msSearch big blocks of text in one pass, across all cores, instead of one line at a time.
Typing in the Find bar on that file (highlight and jump)537 ms1.6 msThe same scan, and files over 4 million characters are searched off the UI thread.
Select every occurrence746 ms102 msCheck word boundaries on the text instead of one rope lookup per match.

Known limits

  • One very long line is slow: a 3 MB minified file costs about 47 ms per keystroke, because the whole line is laid out each frame.
  • After a jump far into a big file, colors can be slightly off until you scroll through it, if a block comment opened further up.
  • Find runs on every keystroke; on a 35 MB file that is about 2 ms, using all cores. A pattern that matches across a line break falls back to a slower line-by-line scan.
  • Start-up includes about 130 ms of window and GPU setup that happens before mide's own code runs.
  • Numbers come from one Apple Silicon Mac. Run the suite on yours.

Reproduce it

Use a release build; debug numbers are meaningless.

git clone https://github.com/kmr-rohit/mide.git && cd mide
scripts/perf.sh --quick      # about a minute, 100,000-line file
scripts/perf.sh              # full run, 1,000,000-line file
scripts/perf.sh --json       # also refresh the data behind this page

Or run one part:

cargo run --release -p mide-bench -- --filter search
MIDE_PERF=1 MIDE_PERF_TYPING=200 MIDE_PERF_EXIT=1 target/release/mide some/file.rs

The scripted app run needs the window to stay visible: macOS stops drawing a covered window, and the script warns when it collects too few samples. For deeper profiling, use Instruments (Time Profiler, Metal System Trace, Allocations); the repository's docs/notes/PERFORMANCE.md has the commands.
